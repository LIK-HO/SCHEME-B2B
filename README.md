# SCHEME-B2B

Простой зрелый B2B-контур поиска для Москвы.

Цель:
Поиск -> Очистка -> Глобальная дедупликация -> Проверка реквизитов -> Приоритизация -> Передача оператору -> Результат -> Уведомления.

## Архитектура

Единый монолит без микросервисов:

- FastAPI — HTTP/API и health endpoints.
- Search service — единый orchestration pipeline.
- Airtable adapter — рабочий контур 01/02/03/10/20/30.
- FNS verifier — формальная проверка реквизитов и подключаемый официальный verification adapter.
- Notification outbox — независимое состояние MAX и Email.
- SQLite — локальный технический журнал запусков и ошибок; отдельный SQLite индекс используется для быстрого подтверждения ФНС.
- GitHub Actions — scheduled runner для public repository.
- Docker — переносимый production runtime.

Airtable остаётся операционным интерфейсом. Бизнес-правила поиска и дедупликации находятся в коде, а не размазаны по десяткам автоматизаций.

## P0: глобальная дедупликация

До создания новой записи проверяется весь периметр:

1. 01 Компании
2. 02 Клиенты
3. 03 Архив

Основной ключ — нормализованный ИНН.

Правило: существующая запись подавляет повторный импорт. Это действует независимо от её текущего статуса.

## P1: проверка реквизитов

Проверяются:

- длина и цифровой формат ИНН;
- контрольные суммы ИНН;
- контрольная сумма ОГРН;
- контрольная сумма ОГРНИП;
- согласованность типа реквизита.

Фактическая проверка наличия/статуса в ЕГРЮЛ/ЕГРИП вынесена в отдельный FNS adapter. Секреты и служебные доступы не зашиваются в репозиторий.

## Уведомления

MAX и Email — независимые каналы.

Сначала событие фиксируется в Airtable 30 Уведомления. Затем dispatcher отправляет каждый канал отдельно. Ошибка одного канала не блокирует другой.

Поддерживаются retry и backoff. Идентификатор события используется как idempotency key.

## Запуск

~~~bash
python -m pip install -e ".[dev]"
pytest -q
python -m scheme_b2b run-once
python -m scheme_b2b dispatch-outbox
python -m scheme_b2b build-fns-index --path /data/fns/egrul.zip
uvicorn scheme_b2b.main:app --host 0.0.0.0 --port 8080
~~~

## Переменные окружения

Скопируйте .env.example в .env.

Обязательные для Airtable:

- AIRTABLE_TOKEN
- AIRTABLE_BASE_ID

По умолчанию в конфигурации уже указаны технические IDs текущего рабочего проекта. Их можно переопределить environment variables.

Для GitHub Actions токен Airtable хранится только в GitHub Secrets.

## График

GitHub Actions запускает worker три раза в сутки:

- 06:07 Москва
- 14:07 Москва
- 22:07 Москва

Сам worker читает частоту из 10 Поиск. Поэтому три scheduled invocations не означают три фактических поиска для профиля 1 раз в день.

## Официальные snapshots

Большие официальные XML/ZIP выгрузки не кладутся в Git. Для постоянного режима храните их на машине с persistent storage, затем выполняйте:

    python -m scheme_b2b build-fns-index --path /data/fns/egrul.zip

После построения FNS_MODE=bulk-index позволяет проверять реквизиты через локальный индекс без повторного полного сканирования реестра.

## Ограничения первого промышленного контура

Crawler для каждого внешнего источника не привязан к неофициальным API. Источники подключаются через adapter contract и проходят отдельную проверку.

Первый релиз сознательно не делает web-scraping Яндекс Карт внутри ядра: это было бы менее стабильно, чем официальные/открытые источники и отдельные проверяемые adapters.

## Важное

GitHub Actions используется как runner, а не как архитектурная зависимость. Сам монолит можно запускать на обычном сервере, Docker host или другом CI runner без переписывания core.


## Защитные лимиты

На один запуск применяются ограничение кандидатов на каждый источник и ограничение новых записей. Достижение лимита явно отражается как неполный запуск, чтобы объём обработки не оставался скрытым.

## Контроль зрелости

Репозиторий содержит два обязательных инженерных документа:

- `docs/QUALITY_BENCHMARK.md` — расширенная benchmark-библиотека зрелых CRM/MDM/data/reliability систем и перевод их практик в проверяемые свойства ядра.
- `docs/RELEASE_GATE.md` — обязательные release-инварианты, recovery/concurrency правила и SLI/SLO первого рабочего контура.

Ядро не зависит от Airtable automation для своих критических бизнес-решений. Для одного persistent runtime поиск и dispatcher сериализуются durable lease; после аварийного завершения просроченный lease может быть безопасно восстановлен.


## Production

Для постоянной автоматизации рекомендуется persistent Docker/VPS runtime с локальным хранилищем snapshots и FNS index. GitHub Actions оставлен как CI и временный scheduler, но не используется как место хранения больших государственных выгрузок.


## Граница системы

Проект намеренно ограничен небольшим рабочим массивом: Discovery -> Normalize -> Identity/Dedup -> Verification/Freshness -> Qualification -> Core/Projection -> Run/Recovery -> Notification -> Operator UI. Это не заготовка универсальной CRM и не повод бесконечно добавлять подсистемы.

Подробно: docs/SYSTEM_BOUNDARY.md и docs/OPERATOR_CONTRACT.md.

После прохождения release gate действует stop rule: новые функции принимаются только при доказанной операторской пользе и понятном влиянии на надёжность.

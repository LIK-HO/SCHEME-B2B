# System boundary: SCHEME-B2B

Дата: 2026-09-19

## Назначение

SCHEME-B2B — не универсальная CRM, ERP или BI-платформа. Это небольшой рабочий инструмент одного оператора для одной задачи:

**найти подходящую B2B-компанию в Москве → доказать её идентичность → понять потребность/сигнал потребности → дать оператору пригодный контакт → не показывать повторно уже обработанную компанию.**

Автоматизация, уведомления и панель управления обслуживают эту задачу и не являются самостоятельной целью.

## Минимальный инженерный массив

Система ограничивается девятью слоями. Новые слои не добавляются без отдельного доказательства необходимости.

### 1. Discovery
Получает кандидатов из разрешённых источников.

Требование: источник должен иметь понятное происхождение, формат, ограничения и способ повторного запуска.

### 2. Normalize
Приводит ИНН, ОГРН/ОГРНИП, название, телефон, email, сайт, город и другие поля к канонической форме.

Требование: одинаковый вход даёт одинаковый результат; нормализация не является доказательством факта.

### 3. Identity + Dedup
Определяет сущность компании и не допускает повторного создания по устойчивому ключу.

Основной детерминированный ключ первого контура — нормализованный ИНН; ОГРН/ОГРНИП подтверждает тип юридического лица/ИП.

Требование: uniqueness обеспечивается core, а не только интерфейсом или автоматизацией Airtable.

### 4. Verification + Freshness
Проверяет обязательные реквизиты и актуальность авторитетного источника.

Требование: checksum, классификация или эвристика никогда не выдаются за официальное подтверждение. Устаревший источник не считается свежим.

### 5. Qualification
Формирует минимальный рабочий профиль: география, сфера, потребность/сигнал потребности, контактный канал и приоритет.

Требование: приоритет помогает оператору сортировать работу, но не подменяет фактическую проверку.

### 6. Core + Projection
Core хранит технически значимую идентичность, историю запуска и результат обработки. Airtable является подключаемой рабочей проекцией.

Требование: потеря/недоступность проекции не должна создавать новую сущность в core.

### 7. Run + Recovery
Один контролируемый запуск, явные исходы, timeout, bounded retry, lease и автоматическое восстановление после падения.

Требование: повторный запуск безопасен; зависшие состояния имеют путь восстановления без ручного вмешательства.

### 8. Notification
Результат запуска передаётся оператору через независимые каналы.

Требование: уведомление не является источником истины и не должно ломать поиск.

### 9. Operator UI
Оператору доступны только действия, необходимые для ежедневной работы.

Требование: технические поля остаются в системе для аудита, но не обязаны быть видимыми в основном рабочем экране.

## Что входит в первый рабочий контур

Обязательно:

- поиск по Москве;
- выбор сферы;
- ограничение объёма;
- автоматический/ручной запуск;
- глобальная дедупликация;
- проверка реквизитов;
- проверка актуальности обязательного источника;
- вывод компании, ИНН, реквизитов, сферы, потребности, контактов и источника;
- статусы «ожидает → принят/отклонён»;
- журнал запуска;
- повторное выполнение после временного сбоя;
- итоговое уведомление.

## Что намеренно не входит

До появления измеренной потребности не добавляются:

- микросервисы;
- отдельные event-bus/queue-кластеры;
- сложный AI-agent layer;
- собственный BI;
- тяжёлый data warehouse;
- десятки CRM-сущностей;
- сложная ролевая модель;
- визуальные дашборды ради дашбордов;
- десятки автоматизаций поверх одного бизнес-правила;
- нестабильный scraping как обязательная часть core;
- платные enrichment-сервисы как скрытая зависимость бесплатного контура.

## Ключевая продуктовая граница

Наиболее важный недостающий элемент текущего бесплатного контура — **качественный discovery/enrichment источник с контактами и сигналом потребности**. Государственные реестры хорошо подтверждают существование и классификацию компании, но сами по себе не решают задачу поиска рабочего контакта и текущей потребности.

Поэтому следующий source adapter должен добавляться только после проверки его лицензии, стабильности, стоимости и права на хранение данных. Яндекс API Поиска по организациям действительно предназначен для поиска организаций и контактов, но его текущая коммерческая лицензия запрещает сохранять или изменять полученные данные; следовательно, его нельзя молча превращать в постоянный бесплатный master-dataset. Это отдельный adapter/операторский lookup, если он когда-либо будет экономически и юридически оправдан.

## Stop rule

После выполнения обязательного массива выше проект переходит в режим **maintenance + evidence**.

Каждое новое изменение обязано ответить на четыре вопроса:

1. Какую операторскую проблему оно решает?
2. Какую существующую простую часть системы оно заменяет или улучшает?
3. Каким тестом/метрикой доказывается польза?
4. Какой новый отказ и технический долг оно добавляет?

Если доказанного ответа нет — изменение не принимается.

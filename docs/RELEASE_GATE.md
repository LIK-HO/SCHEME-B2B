# Release gate

Дата: 2026-09-18

Это обязательный контроль перед переводом SCHEME-B2B из разработки в рабочий контур.

## A. Correctness

- Пакет компилируется без ошибок.
- Ruff не находит нарушений.
- Форматирование Ruff совпадает с кодовой базой.
- Все тесты проходят.
- Покрытие не ниже 70%.
- Собираются sdist и wheel.
- Docker image собирается.

## B. Business invariants

- Одинаковый нормализованный ИНН не должен создаваться повторно в глобальном периметре 01/02/03.
- Некорректный ИНН/ОГРН/ОГРНИП не проходит P1.
- 10-значный ИНН использует ОГРН; 12-значный — ОГРНИП.
- При обязательной проверке ФНС отсутствие актуального подтверждения не превращается в success.
- Неоднозначный ответ внешнего create не вызывает слепной повторной вставки.
- Ошибка одного источника или канала не маскируется под полную успешность запуска.

## C. Concurrency and recovery

- В одном локальном runtime одновременно выполняется не более одного search-run.
- В одном локальном runtime одновременно выполняется не более одного outbox-dispatch.
- Lease имеет срок действия и может быть безопасно восстановлен после падения процесса.
- Освободить lease может только текущий владелец.
- Просроченный lease можно перенять без ручного вмешательства.

## D. Data freshness and provenance

Каждая принятая запись должна иметь:

- источник кандидата;
- дату обнаружения;
- результат фактической проверки ФНС или явное состояние отсутствия проверки;
- источник проверки ФНС;
- run_id в техническом журнале.

Для государственных snapshot-источников дата источника контролируется отдельно от даты локального rebuild.

## E. External failure policy

Повторяем только потенциально временные ошибки. Для retries используются конечное число попыток, timeout, exponential backoff и jitter. Ошибки валидации/конфигурации не ретраятся как будто они временные.

## F. Readiness

/health отвечает только за liveness.

/ready должен возвращать ошибку до начала небезопасной обработки, если:

- отсутствует Airtable token;
- отсутствует API key;
- нет ни одного корректно настроенного источника;
- обязателен FNS, но его режим/URL/snapshot/index отсутствует или неактуален.

## G. SLI / SLO для первого рабочего контура

Это операционные цели проекта, а не значения, приписываемые какому-либо внешнему вендору.

| SLI | SLO |
|---|---|
| Дубли по ИНН, созданные core | 0 подтверждённых нарушений в тестовом/контролируемом периметре |
| Немая потеря запуска | 0: каждый запуск имеет success/partial/error/skipped |
| Ошибки обязательной проверки, скрытые как подтверждение | 0 |
| Дублирование outbox-задач для одного event_id+канала | 0: одна логическая задача на событие и канал |
| Необработанное зависшее состояние после lease expiry | автоматическое восстановление |
| CI release gate | 100% обязательных job зелёные перед merge |

## H. Production boundary

На первом этапе допускается один активный worker runtime с persistent storage. GitHub Actions может быть scheduler/CI, но не является источником истины и не должен хранить постоянные государственные snapshots.

Доставка внешнего Email/MAX по своей природе остаётся at-least-once: если процесс успел отправить сообщение, но потерял ответ провайдера, без provider-side idempotency/reconciliation абсолютное ровно-однократное сообщение не гарантируется. Core обязан не плодить логические outbox-задачи, а внешний контракт должен быть усилен idempotency provider, когда он доступен.

При появлении нескольких активных worker-hosts локальный SQLite lease должен быть заменён распределённым механизмом блокировок с теми же контрактами. Это отдельное изменение архитектуры, а не скрытая попытка сделать SQLite распределённым.

## I. Запрещённые shortcuts

- отключать тесты ради зелёного CI;
- понижать coverage gate ради сборки;
- считать checksum официальным подтверждением;
- повторять POST/create без idempotency/reconciliation;
- превращать внешний timeout в «компания не существует»;
- использовать AI как доказательство юридического факта;
- переносить core-правила в неаудируемые UI-автоматизации.

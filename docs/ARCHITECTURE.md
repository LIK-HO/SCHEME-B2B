# Архитектура SCHEME-B2B

## Решение

Выбран монолит с внутренними модулями, а не набор микросервисов.

Причины:

- один оператор;
- небольшой объём данных на первом этапе;
- минимальная инфраструктура;
- единая orchestration-логика;
- проще аудит;
- меньше точек отказа;
- переносимость на другой runner или сервер;
- возможность постепенно менять adapters без изменения core.

## Инварианты

### D1 — Глобальная уникальность

До insertion worker обязан проверить INN в:

- 01 Компании;
- 02 Клиенты;
- 03 Архив.

Повторная запись не создаётся.

### D2 — Формальная валидность

Строка похожая на ИНН не считается достаточным доказательством. Контрольная сумма обязательна.

### D3 — Источник истины

Airtable хранит рабочее состояние и операторский интерфейс.

GitHub хранит исходный код.

Секреты находятся только в environment/GitHub Secrets/secret manager.

### D4 — Независимые каналы

MAX и Email имеют разные записи outbox и разные состояния доставки.

### D5 — Idempotency

Event ID содержит run ID и канал. Повторный dispatcher не создаёт второе событие.

### D6 — Fail closed

При невозможности пройти обязательную проверку система не делает молчаливое предположение.

## Pipeline

Source -> Normalize -> P0 global dedup -> P1 requisites -> FNS adapter -> Priority -> Airtable -> Outbox -> MAX/Email

## Источники

Стабильный интерфейс CandidateSource отделяет ядро от конкретного источника.

Источник обязан возвращать нормализуемый набор полей:

company, inn, ogrn/ogrnip, city, sector, need, phone, email, website, responsible, source.

## Планировщик

В GitHub Actions есть три расписания. Worker дополнительно читает:

- Активен
- Автопоиск
- Частота поиска
- Последний запуск

Таким образом расписание runner не заменяет бизнес-правило частоты.

## Production перенос

Для постоянного серверного режима тот же пакет запускается под Docker/uvicorn. Scheduler может быть заменён внешним cron без изменения pipeline.

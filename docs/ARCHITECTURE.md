# Архитектура SCHEME-B2B

## Решение

Выбран монолит с внутренними модулями, а не набор микросервисов.

Причины:

- один оператор;
- небольшой объём данных на первом этапе;
- минимальная инфраструктура;
- единая orchestration-логика;
- проще аудит;
- меньше точек отказа;
- переносимость на другой runner или сервер;
- возможность постепенно менять adapters без изменения core.

## Инварианты

### D1 — Глобальная уникальность

До insertion worker обязан проверить INN в:

- 01 Компании;
- 02 Клиенты;
- 03 Архив.

Повторная запись не создаётся.

### D2 — Формальная валидность

Строка похожая на ИНН не считается достаточным доказательством. Контрольная сумма обязательна.

### D3 — Источник истины

Airtable хранит рабочее состояние и операторский интерфейс.

GitHub хранит исходный код.

Секреты находятся только в environment/GitHub Secrets/secret manager.

### D4 — Независимые каналы

MAX и Email имеют разные записи outbox и разные состояния доставки.

### D5 — Idempotency

Event ID содержит run ID и канал. Повторный dispatcher не создаёт второе событие.

### D6 — Fail closed

При невозможности пройти обязательную проверку система не делает молчаливое предположение.

## Pipeline

Source -> Normalize -> P0 global dedup -> P1 requisites -> FNS adapter -> Priority -> Airtable -> Outbox -> MAX/Email

## Источники

Стабильный интерфейс CandidateSource отделяет ядро от конкретного источника.

Источник обязан возвращать нормализуемый набор полей:

company, inn, ogrn/ogrnip, city, sector, need, phone, email, website, responsible, source.

## Планировщик

В GitHub Actions есть три расписания. Worker дополнительно читает:

- Активен
- Автопоиск
- Частота поиска
- Последний запуск

Таким образом расписание runner не заменяет бизнес-правило частоты.

## Production перенос

Для постоянного серверного режима тот же пакет запускается под Docker/uvicorn. Scheduler может быть заменён внешним cron без изменения pipeline.


## Надёжность и границы

- **Fail-closed:** при обязательной проверке ФНС кандидат не проходит дальше без подтверждения через `official`, `bulk` или свежий `bulk-index`.
- **Свежесть данных:** FNS index считается актуальным по фактической `ДатаВыг` snapshot, а не по времени его локальной индексации.
- **Идентификатор реестра:** записи индекса ключуются по ОГРН/ОГРНИП; ИНН используется как дополнительный индекс. Это соответствует модели замещающих записей ФНС.
- **Глобальный dedup:** существующие ИНН предварительно загружаются из 01/02/03 одним снимком на запуск, после чего проверка выполняется в памяти.
- **Ограничение повреждения:** установлен лимит кандидатов на источник и лимит новых записей за один запуск; достижение лимита делает результат `partial`, а не незаметным `success`.
- **Источник ошибок:** ошибка одного источника не скрывается; она входит в итог запуска и меняет его статус на `partial`, если другие источники продолжили работу.
- **Выходной контур:** MAX и Email идут отдельными outbox-событиями с idempotency key.
- **Leasing:** перед внешней доставкой outbox фиксирует окно аренды через `Следующая попытка`; после сбоя применяется exponential backoff с jitter.
- **API:** write-endpoints работают только при заданном API key; отсутствие ключа является ошибкой конфигурации.
- **Health/readiness:** `/health` — liveness; `/ready` проверяет Airtable, API key, наличие источника и требования выбранного FNS-режима.

## Производственная граница

GitHub Actions рассматривается как временный runner/CI, а не постоянное хранилище больших реестров. Для промышленного цикла snapshot ФНС должен находиться на persistent storage рядом с worker; после обновления строится индекс и только затем запускается поиск. Это устраняет зависимость бизнес-цикла от эфемерного runner.
